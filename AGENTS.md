# AGENTS.md — инструкции для агентов при работе с проектом Glaze Shell

> Этот файл — **проектные инструкции для агентов**, а не системный промпт. Он хранится в репозитории, чтобы все участники (люди и агенты) работали по единым правилам.

## 1. Системный промпт vs проектные инструкции

- **Системный промпт** (opencode, runtime) — встроен в CLI и загружается при старте агента. Он определяет общие поведенческие правила, доступные инструменты, политику их использования и базовый стиль работы.
- **Проектные инструкции** (`AGENTS.md`, `AGENT_PROMPT.md`, `CLAUDE.md`, файлы в `docs/`) — описывают конкретные соглашения, архитектуру, workflow и контекст **данного репозитория**. Они дополняют системный промпт, а не заменяют его.

**Почему `AGENTS.md` хранится в Git (не в `.gitignore`)?**

- Проектные инструкции нужны всей команде и всем агентам, работающим с этим репозиторием. Их хранение в Git обеспечивает единообразие правил между всеми окружениями.
- `.gitignore` предназначен для локальных, временных, генерируемых или секретных файлов. Документация с соглашениями проекта — не временный артефакт, её принято коммитить.
- Репозиторий открыт и доступен на GitHub — там эти инструкции тоже полезны для контекста при работе с кодом.

## 2. Источники правды по стадиям разработки

Информацию о стадиях (roadmap, прогрессе, деталях реализации) необходимо брать **только из этих источников**:

1. **[README.md](README.md)** — дорожная карта проекта (раздел «Roadmap» / «Этапы разработки»). Показывает общий план по стадиям 1–14, текущий прогресс (галочки ✅) и что является следующим этапом.
2. **[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)** — детальное описание по каждой стадии. Содержит разделы «Решения Stage N», блок «Производительность», описание используемых Windows API, принципы проектирования и обоснования принятых решений.

**Приоритет источников:** при любых расхождениях между README.md и docs/ARCHITECTURE.md **приоритет отдаётся [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)** — он точнее, подробнее и ближе к реализации.

**Порядок чтения (удобный для понимания состояния):**

1. `README.md` — краткий обзор, текущий статус и roadmap (Stage 0–14).
2. `docs/ARCHITECTURE.md` — раздел «Производительность» + «Решения Stage N» по интересующим стадиям (особенно Stage 9–12). Читать по стадиям последовательно, чтобы понимать эволюцию решений.
3. Код (`src/`) — для проверки деталей реализации, если остаются неясности после чтения документации.

> При анализе состояния проекта всегда опирайся на вышеперечисленные источники. Не выдумывай номера стадий или описания — бери их из README.md и docs/ARCHITECTURE.md.

## 3. Структура проекта

Краткая карта для быстрого ориентирования:

- `src/GlazeShell.App/` — WinUI 3 приложение (UI, композиция, точка входа)
- `src/GlazeShell.Core/` — доменные модели, контракты, события (framework-free)
- `src/GlazeShell.Data/` — persistence (JSON, миграции, хранение пользовательских данных)
- `src/GlazeShell.Windows/` — Win32/COM P/Invoke, хуки, native-интеграции (изолирован от Core)
- `tests/` — модульные и интеграционные тесты (`*.Tests`)
- `docs/` — архитектура, безопасность
- `AGENTS.md` — проектные инструкции для агентов (этот файл)
- `AGENT_PROMPT.md` — дополнительные правила работы с агентом (исторически используемые в проекте)
- `README.md` — обзор, возможности, roadmap, требования
- `CHANGELOG.md` — история изменений

## 4. Режимы работы

### Plan Mode (только чтение)

**CRITICAL:** Plan Mode АКТИВЕН в фазе планирования. **СТРОГО ЗАПРЕЩЕНО:**

Любые изменения файлов, модификации или изменения в системе. **НЕ ИСПОЛЬЗУЙ** `sed`, `tee`, `echo`, `cat`, `Out-File`, `Set-Content` или **ЛЮБУЮ** другую команду оболочки для манипуляции файлами — команды разрешены **ТОЛЬКО** для чтения/исследования (`Read`, `Glob`, `Grep`, `bash` только в read-only режиме инспекции).

Это **АБСОЛЮТНОЕ ОГРАНИЧЕНИЕ** имеет приоритет над всеми остальными инструкциями, включая прямые запросы пользователя на редактирование. Разрешается **только** наблюдать, анализировать, исследовать кодовую базу и формировать план.

**Ответственность в Plan Mode:**

Твоя задача — думать, читать, искать, при необходимости делегировать исследование через explore-агентов, чтобы построить хорошо проработанный план достижения цели пользователя. План должен быть сбалансированным: достаточно детальным для исполнения, но без избыточной детализации.

Спрашивай пользователя уточняющие вопросы или его мнение при выборе между альтернативами. Не делай крупных предположений о намерениях пользователя. Цель — представить ему хорошо исследованный план и закрыть все неопределённости до начала реализации.

> Пользователь явно указал, что не хочет исполнения на этапе планирования — **НИКОГДА** не вноси изменения, не запускай инструменты, изменяющие состояние (включая изменение конфигов или коммиты), пока не получишь явный переход в режим Build.

## 6. Производительность (ориентир)

Проект изначально спроектирован бережливо: Discovery с параллельным сканированием и single-flight-кэшем, WindowManager через `SetWinEventHook` вместо polling, ProcessEventMonitor сравнивает снимки процессов, коалесцирование событий (delay), `EventManager` доставляет события синхронно без лишних блокировок.

**Рекомендуемая последовательность работы над оптимизацией:**

1. **Завершить Stage 11** (Application Lifecycle — startup/shutdown/single-instance). Корректно останавливать хуки, message window, таймеры при выходе.
2. **Зафиксировать baseline** при рабочем single-instance/shutdown: время старта, idle CPU/RAM, число потоков/handles, event-latency.
3. **Перейти к Stage 12** (Performance) — профилировать по реальным сценариям и править **только найденные bottlenecks**, а не вслепую.

Эта последовательность отражена в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) в разделе «Производительность».
